# План тестов: Фильтры + Товары + Подкатегории (детальная страница акции)

Страница: `/useful/shares/{slug}/` — категории → подкатегории → фильтры → товары.
Статус: **план, тесты ещё не реализованы**. Черновые ID кейсов — `FP-xxx`.

Существующее покрытие по теме уже есть в `cypress/e2e/Regress_Test/actions/detail.cy.js`
(`DET-014` подкатегории, `DET-019/DET-024/DET-027` базовая фильтрация) — этот план его
не дублирует, а добавляет нестандартные/граничные кейсы поверх.

---

## Что подтверждено живым осмотром сайта (2026-08-04)

- **Фильтры полностью зависят от категории/подкатегории.**
  У «ПК, ноутбуки, периферия» → «Ноутбуки и аксессуары» — всего 3 группы фильтров
  (Цена, Бренд, Есть скидка). У «Техника для дома» → «Техника для уборки дома»
  (=Пылесосы) — 11 групп (Цена, Бренд, Есть скидка, Специальные предложения,
  Наличие в магазине, Наличие, Сбор жидкости, Уровень шума, Тип питания,
  Турбощётка в комплекте, Цвет корпуса).
- **Подкатегория переиспользует тот же query-параметр `category`** (не отдельный
  `subcategory=`) — клик по подкатегории меняет `?category=tehnika-dlya-doma` на
  `?category=uborka-doma`. Ловушка для тестов на «сброс/сохранение других фильтров
  при смене подкатегории».
- **Применение фильтра — не XHR, а полная навигация.** Чек одного чекбокса ничего
  не отправляет на сервер; данные подтягиваются только по клику
  «Показать N результатов», и это полноценный переход по URL с
  `properties[brend][]=...`, а не fetch/XHR как у каталога акций
  (`/api/v3/promotions**`). Подход `cy.intercept` из `catalogPage.js`/`detailPage.js`
  тут напрямую не сработает — нужен отдельный шаг разведки, чем конкретно
  рендерится страница (SSR/RSC-payload), прежде чем писать перехват.
- **Счётчики соседних фильтров пересчитываются "вживую" ещё ДО клика «Показать»**
  — чисто на клиенте. Пример: чек «Есть скидка → Да» мгновенно обнулил бренды
  Thomas/BORK/Gorenje/Xiaomi (0 результатов), хотя запрос ещё не ушёл. Это и есть
  механизм «недоступных» фильтров — они не задизейблены визуально, просто получают
  счётчик 0.
- **Список опций внутри группы пересортировывается по count** при изменении других
  фильтров (было алфавитно, стало по убыванию количества) — ловушка для тестов,
  кликающих по фиксированным координатам/индексу вместо поиска по тексту.
- **«Показать все» у бренда открывает поиск (input «Поиск»)** внутри списка опций
  — отдельный сценарий для длинных списков фильтров.

## Кейсы

### Разведка (шаг 0, перед написанием тестов)
- **FP-000**: найти реальный запрос, который отдаёт список фильтров/товаров
  категории (перехватить через DevTools/Network — SSR-документ или скрытый
  data-запрос), и только потом писать `cy.intercept`, сверяясь с
  `interception.response.body` вместо предположений.

### Подкатегории меняют фильтры
- **FP-001**: категория без выбранной подкатегории показывает объединённые фильтры
  по всем подкатегориям (счётчики — сумма).
- **FP-002**: выбор подкатегории меняет набор ГРУПП фильтров (не только значения)
  — сверить конкретный факт: у одной подкатегории есть «Сбор жидкости»/«Уровень
  шума», у родительской категории их нет.
- **FP-003**: выбор подкатегории меняет диапазон «Цена» (min/max) на
  соответствующий именно этой подкатегории.
- **FP-004**: повторный клик по той же подкатегории — сброс к родительской
  категории (или полный сброс, по аналогии с CAT-013/CAT-026 — фактическое
  поведение нужно перепроверить, не гадать).
- **FP-005**: переключение между двумя подкатегориями без применения —
  применённые фильтры одной подкатегории не переносятся в другую (или
  сбрасываются — зафиксировать факт).

### Один фильтр
- **FP-010**: выбор одного значения фильтра (например бренд) → клик
  «Показать N» → URL содержит `properties[...][]=...`, список товаров = N.
- **FP-011**: счётчик у выбранного значения фильтра ДО применения соответствует
  счётчику товаров ПОСЛЕ применения.

### Несколько фильтров
- **FP-020**: два значения в ОДНОЙ группе (например два бренда) — логика ИЛИ
  внутри группы, итоговый count ≥ каждого по отдельности.
- **FP-021**: два фильтра из РАЗНЫХ групп (бренд + «Есть скидка») — логика И
  между группами, итоговый count ≤ меньшего из двух.
- **FP-022**: URL корректно содержит оба параметра одновременно, порядок выбора
  не ломает итог (выбрать в одном порядке, потом в обратном — результат
  совпадает).

### 4+ фильтра
- **FP-030**: выбрать 4+ значения фильтров из разных групп → проверить, что на
  странице отображается ИМЕННО пересечение (сверка с фактическим списком
  товаров, а не просто «список не пуст»).
- **FP-031**: 4+ фильтра, дающие пересечение = 0 → сообщение «не найдено» (по
  аналогии с BUG-002 в каталоге акций — проверить, воспроизводится ли тот же баг
  здесь).
- **FP-032**: 4+ фильтра, при которых ещё остаются доступные (не обнулённые)
  значения в других группах — их можно доснять/добавить пятый.

### Недоступные фильтры
- **FP-040**: после выбора одного фильтра другие значения в других группах,
  дающие пересечение 0, показывают счётчик «0» ещё ДО клика «Показать» (живой
  пересчёт на клиенте).
- **FP-041**: клик по значению фильтра со счётчиком «0» — проверить факт:
  срабатывает ли клик вообще (если да — что показывается: пустой список или «не
  найдено»); если задизейблено — чем именно (pointer-events, aria-disabled), как
  в CAT-015/016 у каталога акций.
- **FP-042**: значение с count=0, полученное живым пересчётом, при СБРОСЕ
  конфликтующего фильтра возвращает свой первоначальный ненулевой счётчик.

### Нестандартные комбинации (в духе `catalog_combinations.cy.js`)
- **FP-050**: смена подкатегории при уже применённых фильтрах — сбрасываются ли
  фильтры или переносятся (частично/полностью).
- **FP-051**: сортировка + фильтры вместе — сортировка не теряется при
  применении фильтра (или теряется — зафиксировать факт, отдельно от поведения
  каталога акций, где смена фильтра явно сбрасывает sortBy).
- **FP-052**: список опций внутри группы «Бренд» пересортировывается по count
  при чеке фильтра в другой группе — тест должен искать элемент по тексту, а не
  по индексу/координате (сам факт пересортировки — тоже отдельный кейс).
- **FP-053**: поиск внутри развёрнутого списка «Показать все» — ввод
  несуществующего бренда → пустой результат поиска внутри виджета, без падения
  страницы.
- **FP-054**: прямой переход по URL с фильтром, невалидным для текущей категории
  (например `properties[brend][]=` бренда из другой категории) — не должен
  ломать страницу (аналог CAT-019/BUG-001).
- **FP-055**: быстрое переключение нескольких чекбоксов подряд без клика
  «Показать» — итоговое состояние счётчиков соответствует последнему набору
  чекбоксов, а не гонке промежуточных пересчётов.

## Дальнейшие шаги (когда вернёмся к плану)
1. Согласовать приоритет групп (что делать в первую очередь).
2. Выполнить FP-000 (найти реальный источник данных фильтров/товаров).
3. Оформить кейсы в `.cy.js` по аналогии с `catalog_combinations.cy.js` и
   `detailPage.js`/`catalogPage.js` (page objects).
