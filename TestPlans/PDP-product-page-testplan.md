## Подтверждено разведкой 2026-08-04 (прямые запросы к API, конкретно для `kondicioner-arayplus-fm-07hrn8-s-installyaciey`)

- Товарные эндпоинты (`/api/v3/product/{slug}` и все под-эндпоинты) требуют заголовок
  `X-Mechta-Device-Id: <любая непустая строка>`, иначе `422 device_id_not_provided` —
  как и `/catalog/products` в акциях.
- `onlyShopwindow` — это поле **корневого объекта** `GET /api/v3/product/{slug}`
  (`{..., "onlyShopwindow": true, ...}`), НЕ отдельного эндпоинта.
- **ИСПРАВЛЕНИЕ к постановке задачи**: `GET /api/v3/product/{slug}/similar` — это НЕ
  список "похожих товаров" в обычном смысле, а **виджет выбора варианта товара по
  характеристике** (в данном случае — по площади помещения). Формат:
  ```json
  [{
    "name": "Площадь обслуживаемого помещения",
    "type": "text",
    "products": [
      {"name": "...", "slug": "kondicioner-arayplus-fm-07hrn8-...", "preview": "...", "property": "21 м²", "isCurrent": true},
      {"name": "...", "slug": "kondicioner-arayplus-fm-09hrn8-...", "preview": "...", "property": "27 м²", "isCurrent": false},
      ...
    ]
  }]
  ```
  Само значение "21 м²" для ТЕКУЩЕГО товара уже приходит и в `mainProperties` корневого
  ответа `/product/{slug}`, и продублировано в `/properties` (группа "Основные
  характеристики"). `/similar` нужен конкретно для проверки виджета переключения между
  вариантами (кнопки/чипсы с другими значениями характеристики), а не для самого значения.
  Не у всех товаров этот виджет вообще есть (`/similar` может быть пустым массивом) — это
  нормально, не баг.
- `/reviews?sort=all&page=1` возвращает не только `reviews[]`, но и:
  - `meta`: `{currentPage, totalPages, perPage, totalCount}`
  - `summary`: `{averageRating, reviewsCount, statistics: [{rating: 1..5, count}]}`
  - `sorts`: `[{name, code}]` — доступные варианты сортировки (`all`, `helpful`, `high`, `low`)
  - каждый отзыв: `{id, createdAt, publishedAt, rating, authorName, body, likes, dislikes, userVote, photos}`
    — `userVote` (`null`/вероятно `'like'`/`'dislike'`) это то, что нужно проверять после клика лайк/дизлайк.

## 1. "На витрине" (`onlyShopwindow`)

- **PDP-001** (позитив): товар с `onlyShopwindow: true` в ответе `/product/{slug}` →
  жёлтый стикер "На витрине" виден на странице. Расширить существующий
  `check_only_shop_sticker()`, чтобы он СНАЧАЛА читал `onlyShopwindow` из `@product`,
  а не просто проверял текст стикера "на глаз".
- **PDP-002** (негатив): товар с `onlyShopwindow: false` → стикер "На витрине" НЕ
  отображается в DOM вообще (не просто невидим). Сейчас такого негативного кейса нет.
- **PDP-003** (нестандартный): товар "на витрине" — проверить, что кнопки
  "В корзину"/"Купить сейчас" ведут себя корректно для витринного товара (обычно "на
  витрине" = нет в обычном наличии для доставки, только самовывоз/просмотр в конкретном
  магазине) — сверить с `pickupAvailable`/`availability` в ответе.

## 2. "Способ доставки" (`/shipment` + `/subdivisions`)

Точная логика по ТЗ:
1. `todayDelivery` → блок "Доставка, завтра" (внимание: судя по формулировке, при
   `todayDelivery=false` показывается "завтра"; при `true`, по аналогии, ожидается
   "сегодня" — это предположение, ПРОВЕРИТЬ фактическую формулировку на живом товаре
   с `todayDelivery: true`, если такой найдётся).
2. `expressDelivery: true` → виден блок "Экспресс доставка, за 2 часа"; `false` → блок
   отсутствует в DOM.
3. `pickupAvailable: false` + `subdivisions: N` → блок "Доступно на самовывоз" +
   количество магазинов = N, и список адресов берётся из `/subdivisions`.

Существующий код уже частично покрывает `expressDelivery` и подсчёт магазинов, но
ПОЛНОСТЬЮ по всем 3 полям и особенно по правильной комбинаtorике — нет.

- **PDP-010**: для каждого из 3 полей (`todayDelivery`, `expressDelivery`,
  `pickupAvailable`) — найти живой товар в состоянии `true` И живой товар в состоянии
  `false`, проверить соответствующий блок UI показывается/скрывается ТОЧНО по этому
  полю (не просто "текст есть на странице", а `should('not.exist')` для `false`).
- **PDP-011**: `subdivisions` (число в `/shipment`) ДОЛЖНО совпадать с
  `.length` массива, который реально возвращает `/subdivisions` для того же товара —
  это перекрёстная проверка между двумя эндпоинтами (пример рассинхрона между
  эндпоинтами — отдельный класс бага, см. п.2 критерия бага в скилле).
- **PDP-012** (граничный/негатив): товар, у которого `subdivisions: 0` (если такой
  найдётся) — блок "Доступно на самовывоз" должен корректно показать "нет в наличии для
  самовывоза" или скрыться, а не показать пустой список/сломаться.
- **PDP-013** (нестандартный, пересечение с CRUD-мышлением): клик по кнопке количества
  магазинов открывает список — проверить, что каждый адрес из `/subdivisions` реально
  отображается (уже частично есть в `check_only_shop_adresses`, но та функция фильтрует
  ТОЛЬКО `stock === "На витрине"` — расширить на ВСЕ магазины из ответа, не только
  витринные, и проверить `schedule`/`stock`/`stockProgress` тоже отображаются корректно
  там, где они присутствуют).
- **PDP-014** (не баг, но задокументировать): экспресс-доставка может быть `false` до
  определённого времени суток (см. существующий комментарий в `check_express_delivery`)
  — это не баг, время-зависимое поведение (heuristic: Time из SFDPOT).

## 3. Блок цен (`/offers` + корневой `/product/{slug}`)

Уже частично покрыто (`finalPrice`, `basePrice`, `chips`, `credit`). Добавить:

- **PDP-020**: `bonuses` из `/offers` сравнить с отображаемым количеством начисляемых
  бонусов на странице (сейчас не проверяется вообще).
- **PDP-021**: процент выгоды — вычислить `round((basePrice - finalPrice) / basePrice * 100)`
  и сравнить с отображаемым "-N%" рядом с ценой (если такой элемент есть).
- **PDP-022** (граничный): товар БЕЗ скидки (`basePrice === finalPrice` или
  `discount: 0`) — процент/стикер выгоды не должен отображаться (негативный кейс,
  equivalence partitioning: "скидка есть" vs "скидки нет").
- **PDP-023**: `gifts`/`bundles`, когда они НЕ `null` — `gifts` уже частично покрыт
  (`check_gift_button`), `bundles` — нет вообще. Найти товар с непустым `bundles` и
  проверить его отображение (если такой виджет вообще существует в UI — сначала
  подтвердить разведкой, что бэк для каких-то товаров реально отдаёт непустой `bundles`).
- **PDP-024** (race/non-standard): быстрый повторный клик по "В корзину" — товар должен
  добавиться один раз, а не дублироваться (см. в скилле раздел про race conditions на
  корзине — тут это та же логика, применённая к странице товара).

## 4. "Характеристики" (`/properties` + модальное окно)

- **PDP-030**: ПОЛНОЕ сравнение — для КАЖДОЙ группы и КАЖДОГО свойства в ответе
  `/properties` (не только первых 6 через фиксированные индексы, как сейчас) найти
  соответствующую строку в блоке характеристик на странице. Раз структура — это массив
  групп `{name, properties: [{name, value, url}]}`, итерация должна идти по РЕАЛЬНОЙ
  структуре ответа, а не по захардкоженным `#product-characteristic-key-N` до 6.
- **PDP-031**: клик "Все характеристики" открывает боковую панель — существующий
  `check_vse_charakteristiki()` проверяет только текст дисклеймера. Добавить: панель
  должна содержать ТЕ ЖЕ данные (все группы/свойства из `/properties`), что и основной
  блок на странице — сравнить оба места между собой, не только с API.
  Дополнительно: закрытие панели (крестик/Esc/клик вне) должно работать и не терять
  состояние остальной страницы.
- **PDP-032** (негатив): товар с `properties: []` или отсутствующей группой — блок
  характеристик и кнопка "Все характеристики" не должны падать/показывать пустые строки.

## 5. "Отзывы" — ОТДЕЛЬНЫЙ файл (`reviews.cy.js` или `product_reviews.cy.js`)

Не смешивать с основным `product_page.cy.js` — по объёму и сложности (лайки/дизлайки,
пагинация, сортировка) заслуживает своего файла и своего мини Page Object'а/расширения.

- **PDP-REV-001**: `summary.reviewsCount` совпадает с фактическим количеством карточек
  отзывов, отображённых на первой странице (с поправкой на `meta.perPage`/`totalPages`,
  если отзывов больше одной страницы).
- **PDP-REV-002**: `summary.averageRating` математически согласован с
  `summary.statistics` (сумма `count * rating` по всем 5 звёздам, делённая на
  `reviewsCount`, округлённая — равна `averageRating`; если бэк округляет иначе, тест
  должен сначала подтвердить формулу округления на живых данных, а не гадать).
- **PDP-REV-003**: сумма `statistics[].count` по всем 5 рейтингам равна `reviewsCount`
  (внутренняя согласованность ответа — если не сходится, это баг API уровня "неверный
  подсчёт", попадает под новый критерий бага независимо от UI).
- **PDP-REV-004**: для каждой звезды в `summary.statistics` с `count > 0` — визуальная
  шкала/бар на UI (если есть) отражает это количество (пропорция или число).
- **PDP-REV-005**: смена сортировки (`sorts[].code`: `all`/`helpful`/`high`/`low`) —
  запрос уходит с правильным `sort=`, и порядок карточек фактически меняется
  (для `high`/`low` — по убыванию/возрастанию `rating`; для `helpful` — вероятно по
  `likes`, подтвердить фактическую формулу на живых данных, не предполагать).
- **PDP-REV-006**: пагинация — `meta.currentPage`/`totalPages` соответствуют
  отображаемому номеру страницы и наличию/отсутствию кнопки "следующая страница"; переход
  на несуществующую страницу (`page=9999`) не ломает страницу (негатив/граница).
- **PDP-REV-007** (CRUD-мышление): клик лайк на отзыве → `likes` увеличивается на 1 в UI
  СРАЗУ (оптимистичный апдейт) И после релоада страницы (значит бэк реально сохранил
  голос — проверить прямым `cy.request()` на `/reviews` заново). Повторный клик на тот же
  лайк — снимает голос (`userVote` возвращается в `null`) или меняет на дизлайк — нужно
  сначала разведкой подтвердить фактическую бизнес-логику (toggle vs меняет тип), не
  предполагать.
- **PDP-REV-008** (негатив, авторизация): попытка лайкнуть отзыв БЕЗ авторизации —
  либо предлагает войти, либо голос не засчитывается — подтвердить фактическое
  поведение, не предполагать, что оно совпадает с логикой избранного/корзины.
- **PDP-REV-009** (граничный/негатив): товар без единого отзыва — `summary.reviewsCount:
  0`, `reviews: []` — блок отзывов и счётчик под названием товара не отображаются
  (уже частично покрыто `assertNoReviewsCount`, но не через `/reviews`, а только
  отсутствием счётчика — расширить проверкой самого ответа API).
- **PDP-REV-010** (race, см. скилл п.6): быстрый двойной клик по лайку — итоговое
  состояние соответствует ОДНОМУ голосу, а не гонке (аналогично FP-053 в тестах акций —
  двойной клик может регистрироваться как одно переключение, это нормально, если так и
  оказалось после проверки, задокументировать факт, а не предполагать баг).
