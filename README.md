# MechtaATest

Cypress-тесты и вспомогательные скрипты для тестирования mechta.kz (preprod-стенды
`pp.yc.mechta.kz`, `d2.im.mdev.kz`, `d5.im.mdev.kz`, `pp.im.mdev.kz`).

## Команды для Claude

Быстрый указатель: команда/фраза → что делает. Подробности — по ссылке в последней
колонке. Список будет пополняться — при добавлении новой команды добавляй сюда ещё одну
строку таблицы и свой `###`-раздел ниже по той же схеме, что и `/card-payment-regress`.

| Команда | Фраза-триггер | Коротко что делает | Подробности |
|---|---|---|---|
| `/card-payment-regress` | «Проведи регресс тест по оплате картой» | Живой браузер, 5 кейсов оформления заказа, **реальная оплата** картой, стоп на каждом эквайере до команды «оплатил», сверка API+UI до/после оплаты | [↓ раздел ниже](#card-payment-regress) |

### `/card-payment-regress`

**Регресс оплаты картой (живой браузер, реальные деньги)**

**Файл команды:** `.claude/commands/card-payment-regress.md`
**Полная процедура:** `.claude/skills/mechta-e2e-testing/references/manual-card-payment-regress.md`

#### Как вызвать

Командой `/card-payment-regress` или просто фразой в чате:
> «Проведи регресс тест по оплате картой»

По этой фразе Claude запускает весь прогон целиком, без уточняющих вопросов и без
повторного согласования плана.

#### Что это и зачем

Это **не** обычный автотест из `cypress/e2e/regress_test/checkout_card_payment_*_regress.cy.js`
— те специально останавливаются на редиректе на эквайер, не завершая реальную оплату.
Эта команда — ручной (через живой браузер) аналог того же сценария, но доведённый до
конца: с **реальной оплатой** тестовой картой и проверкой заказа уже **после** оплаты.
Использует ту же логику, что в headless-тестах (страницы чекаута, API), но управляется
интерактивно, потому что ввод карты на странице эквайера — действие, которое обязан
сделать человек (Claude туда не лезет).

#### Стенд и товары по умолчанию

- **Стенд:** `pp.im.mdev.kz` (эквайринг `epay.homebank.kz`, Halyk Payment Page) — как
  текущий рабочий вариант; какой стенд сейчас рабочий, Claude перепроверяет каждый
  прогон (эквайринг уже менялся раньше).
- **Товары:** батарейки Camelion — `batareyka-camelion-cr1632-1-shtdot` и
  `batareyka-camelion-cr2025-bp1-1-shtdot` (~390 ₸ за штуку). Выбраны специально потому,
  что каждый прогон — это реальная трата денег с тестового аккаунта.
- **Аккаунт:** тестовый, телефон `0000000000`, код `0000`. Перед стартом Claude всегда
  проверяет, что залогинен именно тестовый аккаунт, а не реальный номер клиента.

#### Что именно делает Claude — по шагам

Для **каждого** из 5 кейсов подряд:

1. Заходит на стенд, при необходимости логинится под тестовым аккаунтом.
2. Полностью очищает корзину.
3. Добавляет товар(ы) конкретного кейса в корзину.
4. Проходит чекаут: получатель → способ доставки/самовывоза → способ оплаты
   («Картой онлайн»).
5. На каждом шаге сверяет то, что показано на экране, с реальным ответом API
   (`GET /v2/basket`, `GET /v2/checkout` и т.д.) — совпадают ли товары, цены, зона
   доставки, итоговая сумма.
6. Нажимает «Подтвердить заказ» — заказ создаётся на бэкенде.
7. Дожидается редиректа на страницу эквайера (`epay.homebank.kz`).
8. **Останавливается и ждёт** — дальше ничего не делает, пока пользователь сам не введёт
   карту и не напишет в чат «оплатил». Claude никогда не трогает форму оплаты сам.
9. После «оплатил» — открывает страницу заказа и список «Мои заказы», запрашивает
   `GET /v2/personal/order/{id}` целиком и сверяет **все** поля объекта заказа (статус,
   состав, доставку, суммы, флаг оплаты и т.д. — см. «Правила проверки» ниже), а не
   только сумму и статус.
10. Кратко отчитывается по кейсу и переходит к следующему.

#### 5 кейсов по умолчанию

| № | Сценарий |
|---|---|
| 1 | Один товар (cr1632), доставка курьером по самой дешёвой платной зоне города |
| 2 | Оба товара (cr1632 + cr2025), доставка курьером — сумма = товары + зона |
| 3 | Оба товара, самовывоз из первого магазина в списке |
| 4 | Один товар (cr1632), самовывоз из **другого** (второго) магазина |
| 5 | Смена города на Алматы + доставка курьером по местной зоне |

Если пользователь попросит больше кейсов (экспресс-доставка, промокод, списание
бонусов, товар с подарком) — Claude добавляет их по той же схеме и с тем же уровнем
проверки.

#### Правила проверки (обязательно, без выборочности — не только «удобные» поля)

**Главное правило: сверка с API обязательна на каждом шаге, а после оплаты — по ВСЕМ
полям объекта заказа, а не только по сумме и статусу.** Именно так и делалось на живом
прогоне 19.08.2026 — так же делается и дальше, без исключений.

- **Сверка между разными API одного и того же сценария.** Один кейс задействует
  несколько эндпоинтов (`GET /v2/basket`, `GET /v2/checkout`, ответ создания заказа,
  `GET /v2/personal/order/{id}`, `GET /v2/personal/orders_list`) — они должны совпадать
  друг с другом, а не только по отдельности выглядеть правдоподобно на экране. Одно и то
  же название/код/цена товара должны быть одинаковыми во всех этих ответах для одного
  заказа — Claude запрашивает их все и сверяет между собой, а не только один.
- **«Итого» — это формула, и она проверяется по цифрам из API, а не на глаз.**
  `payment_info.total` = сумма товаров (`basket.total_prices.discounted_price`) +
  стоимость доставки (`delivery_info.pay`, 0 для самовывоза) − скидка по промокоду (если
  есть) − потраченные бонусы (если кейс их тратит). Эта сумма считается вручную из
  сырых чисел API и сверяется с тем, что показано в интерфейсе на **каждом** экране, где
  видно «Итого»/«К оплате» — корзина, шаг 2, шаг 3, модалка подтверждения, страница
  эквайера, страница заказа после оплаты, карточка в списке «Мои заказы». Это одна
  сквозная проверка через весь кейс, а не разовое сравнение в конце.
- **Поля товара**: название, код, цена за единицу, количество, сумма по позиции — для
  **каждого** товара в кейсе, не только для первого.
- **Способ доставки/самовывоза**: название и цена зоны/магазина в интерфейсе должны
  совпадать с тем, что отдаёт API.
- **После оплаты — «Детали заказа» по всем полям `order`, не только сумма/статус.**
  Claude запрашивает `GET /v2/personal/order/{id}` целиком и проходит по каждому полю:
  - `current_status` — корректный «оплачен»/«в доставке», не «ожидает оплаты» и не ошибка
  - все товары в `basket.items[]` — с ценами, количеством
  - `basket.total_prices`
  - `order.delivery_info` — адрес, тип доставки, цена, дата
  - `order.payment_info` — `total`, `to_pay`, `bonuses`, `spent_bonuses`
  - `order.payment_info.payments[0]` — `is_paid` (обязательно `true`), `type` (способ
    оплаты), `summ`, `pay_error` (должен быть пустым)
  - текст баннера/summary — не противоречит статусу
  - `created_at`, `city_slug` — адекватные значения
  Построчное сравнение «было до оплаты» ⟷ «стало после оплаты» по каждому из этих полей,
  не выборочно.
- **Список «Мои заказы»** (`/cabinet/orders/`) — отдельно, не только страница
  конкретного заказа: сумма в карточке списка должна совпадать с реальной суммой к
  оплате (именно здесь был найден баг BUG-002/AS-4581 — список показывал сумму без
  учёта доставки).

Любое расхождение — даже в 1 тенге, даже неверная формулировка статуса, даже в поле,
которое раньше не проверялось, — считается кандидатом на баг и заводится по
стандартному процессу: файл в `BugReport/`, запись в README области, тикет в Jira.

#### Ограничения и особенности, о которых стоит знать

- Claude **никогда** не вводит данные карты и не завершает оплату сам — это всегда
  делает пользователь на странице эквайера.
- Страница эквайера может грузиться медленно (до 30–45 секунд) — это нормально, не сбой.
- Расширение claude-in-chrome иногда обрывает соединение с браузером посреди прогона —
  Claude ждёт переподключения и продолжает с того же места.
- Если ранее оплаченный заказ вдруг показывает статус «Отменён» — это может быть
  результатом того, что пользователь сам отменил его между прогонами (кнопка «Отменить
  заказ»), а не баг. Claude уточняет это, прежде чем заводить баг-репорт.
- На стенде `pp.im.mdev.kz` по состоянию на 19.08.2026 нет ни одной бесплатной зоны
  доставки — используется самая дешёвая платная. Актуальность этого факта Claude
  перепроверяет через API при каждом прогоне.
