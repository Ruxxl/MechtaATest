# BUG-005: orders_count.active + cancelled + finished ≠ orders_count.all

**Раздел:** Личный кабинет — Мои заказы, API `GET /v2/personal/orders_list`
**Severity:** Medium
**Приоритет:** Medium
**Статус:** Подтверждён
**Дата обнаружения:** 2026-08-06
**Окружение:** `http://api.d.im.mdev.kz/v2/personal/orders_list` (тестовый стенд d2)

## Предусловия

Авторизованный пользователь с достаточно большим количеством заказов
(текущий тестовый аккаунт).

## Шаги воспроизведения

1. `GET http://api.d.im.mdev.kz/v2/personal/orders_list?status=active&page=1&limit=10`.
2. Взять поле `data.orders_count` из ответа.
3. Сложить `active + cancelled + finished` и сравнить с `all`.

## Ожидаемый результат

Каждый заказ должен относиться ровно к одной из категорий (active / cancelled
/ finished), поэтому `active + cancelled + finished` должно равняться `all`
(либо `all` должен объяснимо отличаться — напр. включать дополнительные
статусы, отсутствующие в трёх перечисленных счётчиках, но тогда это тоже
нужно явно задокументировать).

## Фактический результат

На момент проверки: `{all: 918, active: 800, cancelled: 112, finished: 118}`.

`800 + 112 + 118 = 1030`, что на **112 больше**, чем `all: 918`. Расхождение
воспроизводится стабильно (тот же паттерн уже отмечался в тест-плане на более
ранних данных: `800+110+116=1026` vs `all: 916` — расхождение на те же 110,
т.е. это систематическая, а не случайная погрешность).

Похоже, что `cancelled` считается ДВАЖДЫ: один раз как часть `finished`
(вкладка «Завершённые» объединяет и выполненные, и отменённые — это
подтверждённое ожидаемое поведение самого разбиения на вкладки), и второй
раз как отдельный счётчик `cancelled` — то есть `all` не равен сумме трёх
счётчиков, потому что `cancelled` — не независимая категория, а подмножество
`finished`, и это не учтено при формировании ответа/понимании контракта.

## Повторное подтверждение (2026-08-07)

Живой замер через DevTools Network (`GET /v2/personal/orders_list?status=active&page=1&limit=10`):
`{all: 919, active: 801, cancelled: 112, finished: 118}`.

`801 + 112 + 118 = 1031`, что на **112** больше `all: 919` — разница снова в
точности равна `cancelled`. Уже третий независимый замер с тем же паттерном
(110 → 112 → 112), что подтверждает системный, а не разовый характер
расхождения.

## Вероятная причина

`cancelled` в структуре `orders_count`, судя по всему, задуман как
подмножество `finished` (тот же вывод, что и по значению `112` ≈ разница
`1030-918`), но представлен как если бы он был независимой категорией наравне
с `active`/`finished`. Нужна либо явная документация контракта (что `all` =
`active + finished`, а `cancelled` — просто уточнение состава `finished`),
либо исправление расчёта на бэкенде.

## Автотест, фиксирующий баг

`cypress/e2e/Regress_Test/cabinet/orders.cy.js` — тест сверяет арифметику
`orders_count` через прямой API-запрос и падает, пока расхождение не будет
объяснено/исправлено.
