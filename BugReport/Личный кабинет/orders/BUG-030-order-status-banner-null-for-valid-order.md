# BUG-030: `order_status_banner` — `null` у валидного заказа со статусом `ready_for_pickup`, хотя у всех сравнимых заказов это поле всегда заполнено

**Раздел:** Личный кабинет — Мои заказы (`/cabinet/orders/`, `GET /v2/personal/orders_list`)
**Severity:** Low
**Приоритет:** Low
**Статус:** Подтверждён
**Дата:** 2026-08-10
**Окружение:** `http://d2.im.mdev.kz/`, API `http://api.d.im.mdev.kz`

## Предусловия

Авторизованный пользователь (Джон Appleseed, 0000000000) с большим количеством
реальных заказов (919 на момент проверки) открывает список заказов.

## Шаги воспроизведения

```bash
curl -s -b cookies.txt "http://api.d.im.mdev.kz/v2/personal/orders_list?status=active&page=4&limit=10" \
  -H "X-Mechta-Device-Id: any" | jq '.data.orders[] | select(.order.id=="10392507")'
```

Либо открыть `http://d2.im.mdev.kz/cabinet/order/10392507/` напрямую.

## Ожидаемый результат

`order_status_banner` — required-по-факту объект (`{title, description, type, icon, color}`),
присутствующий у КАЖДОГО из 268 проверенных заказов (выборка по 15 страниц
активных + 15 страниц завершённых), кроме одного. Для заказа со статусом
`ready_for_pickup` он должен быть заполнен так же, как у второго найденного
заказа с тем же статусом (объект с `type`, скорее всего `"ready_for_pickup"`
или аналогичным).

## Фактический результат

У заказа `№ 10392507` (статус `current_status: "ready_for_pickup"`, реальные
данные — не мок) поле `order_status_banner` равно `null` целиком, при том что
`summary` (`title`/`subtitle`) и `statuses` для этого же заказа заполнены
нормально:

```json
{
  "order_id": "10392507",
  "current_status": "ready_for_pickup",
  "summary": {
    "title": {"text": "Заберите товары до 27 июля включительно", ...},
    "subtitle": {"text": "ул. Сыганак, 3 (Е-10)", ...}
  },
  "order_status_banner": null
}
```

Из 268 просмотренных заказов (все статусы: `created`, `canceled`, `completed`,
`ready_for_pickup`, `cancellation_request`) это единственный с `null` —
включая второй заказ с тем же `current_status: "ready_for_pickup"`, у которого
`order_status_banner` заполнен как обычно.

**Живьём проверено, что фронтенд НЕ падает** на детальной странице этого
заказа (`/cabinet/order/10392507/`) — она рендерится корректно, включая
таймлайн статусов и итоговую сумму, потому что этот конкретный экран, судя по
всему, не читает `order_status_banner` напрямую. Не проверено, отличается ли
чем-то визуально карточка этого заказа в СПИСКЕ `/cabinet/orders/` (список
использует `summary.title.text` для основного текста, как уже установлено в
BUG-009, поэтому видимого текста карточка не теряет) — но само по себе
`null` вместо ожидаемого объекта в поле, которое у всех остальных записей
одного типа заполнено, — нарушение внутренней согласованности данных на
уровне API, воспроизводимое и заслуживающее исправления независимо от того,
использует ли его прямо сейчас конкретный экран.

## Скриншоты

Не применимо: детальная страница заказа 10392507 визуально ничем не
отличается от любой другой (что и подтверждает вывод ниже — поле нигде явно
не рендерится, проблема на уровне данных API, а не отображения). Сам дефект
воспроизводится и виден только в сыром ответе API — см. запрос выше.

## Вероятная причина

Похоже на единичный сбой при генерации/миграции `order_status_banner` для
этой конкретной записи (например, статус `ready_for_pickup` был проставлен
вручную/через миграцию данных без пересчёта производного поля баннера) —
не системная проблема для всего типа статуса, раз второй `ready_for_pickup`
заказ в выборке заполнен нормально.

## Автотест, фиксирующий баг

`cypress/e2e/main_test/cabinet/orders.cy.js` → сверка полей с API — тест
проверяет, что `order_status_banner` не `null` для каждого заказа в списке,
и падает на заказе `10392507`, пока данные не будут исправлены на бэкенде.
