# BUG-034: «Выйти» (logout) иногда не завершает сессию на бэкенде — после релоада пользователь снова видит свой кабинет

**Раздел:** Личный кабинет — боковое меню, пункт «Выйти» (воспроизведено с `/cabinet/`, затрагивает всю сессию сайта)
**Severity:** High
**Приоритет:** High
**Статус:** Подтверждён (интермиттентно, ~50% по последней перепроверке)
**Дата:** 2026-08-10, перепроверено 2026-08-12
**Окружение:** `http://d2.im.mdev.kz/` (тестовый), API `http://api.d.im.mdev.kz`

## Предусловия

Пользователь авторизован, находится на `/cabinet/`.

## Шаги воспроизведения

1. Кликнуть «Выйти» в боковом меню ЛК.
2. Дождаться `POST /v2/logout` (реально уходит и отвечает `200
   {result:true, errors:[], data:null}` — успех согласно самому API).
3. Убедиться, что произошёл редирект на `/` (происходит стабильно).
4. Сделать `F5` (полный reload) на `/`.
5. Перейти напрямую на `/cabinet/`.
6. Проверить реальное состояние сессии НАПРЯМУЮ через `GET
   /v2/personal` (не по тексту страницы — см. «Важное методологическое
   уточнение» ниже).

## Ожидаемый результат

После успешного логаута сессия должна быть реально завершена на бэкенде —
`GET /v2/personal` после логаута должен возвращать `401`, не `200
{result:true}`.

## Фактический результат

Воспроизведено многократно через автоматизированные повторные прогоны
(Cypress, реальный стенд, без моков):
- Первичное обнаружение (2026-08-10, 16 повторов через 4 отдельных
  прогона, детекция по тексту страницы): воспроизведено примерно в 11/16
  случаев (~69%).
- Перепроверка 2026-08-12 (по инициативе пользователя, тикет висел в
  статусе «Код ревью»): первый заход — 8 прямых `fetch()`-проверок
  (login→logout→`GET /v2/personal`) подряд без полной загрузки страницы
  между ними — дал **0 из 16** отказов (см. «Методологическое уточнение»
  ниже про то, почему это не опровергает баг). Второй, более реалистичный
  заход — тот же цикл, но с ПОЛНОЙ загрузкой страницы между шагами (реальный
  клик по «Выйти» в UI, `cy.reload()`, повторный `cy.visit()`), с прямой
  кросс-проверкой через `GET /v2/personal` НЕЗАВИСИМО от текста
  страницы — дал **4 из 8** попыток (50%) с сессией, реально ЖИВОЙ на
  бэкенде после логаута (`GET /v2/personal` → `200 {result:true}`) — то
  есть баг по-прежнему воспроизводится, близко к исходным ~69%.

## Важное методологическое уточнение (2026-08-12)

Race, судя по всему, зависит от РЕАЛЬНОГО прошедшего времени/нагрузки между
`POST /v2/logout` и следующим запросом сессии — быстрые последовательные
`fetch()`-вызовы без полной загрузки страницы (SSR, гидратация,
параллельные запросы виджетов и т.д.) реже попадают в окно гонки, чем
реалистичный пользовательский флоу с полными переходами по страницам.
**Поэтому «чистый» результат из быстрого fetch-based теста не может
считаться доказательством фикса** — только тест, максимально близкий к
реальному пользовательскому флоу (с полной загрузкой страниц), даёт
репрезентативную оценку.

Отдельно обнаружено: детекция «залогинен ли пользователь» по ТЕКСТУ
страницы (`$body.text().includes('Ваш баланс') &&
!$body.text().includes('Авторизуйтесь')`), которую использовал прежний
автотест, — **ненадёжный индикатор**. В перепроверке 2026-08-12 текст
страницы разошёлся с реальным ответом `GET /v2/personal` в 3 из 8
попыток — причём в обе стороны: дважды UI показывал «залогинен» при
реально мёртвой сессии не наблюдалось, зато трижды UI показывал
«разлогинен», хотя `GET /v2/personal` подтверждал, что сессия на бэкенде
всё ещё ЖИВА. Вывод: UI-рендер `/cabinet/` при реальном заходе с ещё живой
сессией не всегда успевает/решает показать авторизованные данные в
observation window тесta — то есть регресс-тест, полагающийся на текст
страницы, systематически НЕДООЦЕНИВАЕТ частоту бага. Тест переписан на
прямую проверку через `cy.request('GET', '/v2/personal')` вместо
скрейпинга текста страницы.

## Скриншоты

`screenshots/bug034-cabinet-accessible-after-logout.png` — прямой заход

ожидаемой анонимной версии.

## Вероятная причина

`POST /v2/logout` отвечает `200 {result:true}` немедленно, не дожидаясь
(или не гарантируя) реальной инвалидации сессии/токена на бэкенде —
классическая гонка между «ответить об успехе» и «фактически применить
эффект». С точки зрения ISTQB это дефект API: эндпоинт сигнализирует об
успехе, не выполняя корректно свою обязательную функцию.

## Автотест, фиксирующий баг

`cypress/e2e/main_test/cabinet/cabinet_overview.cy.js` — тест «После
«Выйти» + reload сессия реально завершена на бэкенде (несколько
попыток) — BUG-034» проверяет напрямую через `cy.request('GET',
'/v2/personal')` (не через текст страницы — см. методологическое
уточнение выше) и падает, пока баг не исправлен.
