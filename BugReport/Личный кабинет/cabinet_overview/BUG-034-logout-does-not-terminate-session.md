# BUG-034: «Выйти» (logout) иногда не завершает сессию на бэкенде — после релоада пользователь снова видит свой кабинет

**Раздел:** Личный кабинет — боковое меню, пункт «Выйти» (воспроизведено с `/cabinet/`, затрагивает всю сессию сайта)
**Severity:** High
**Приоритет:** High
**Статус:** Подтверждён (интермиттентно)
**Дата:** 2026-08-10
**Окружение:** `http://d2.im.mdev.kz/` (тестовый), API `http://api.d.im.mdev.kz`

## Предусловия

Пользователь авторизован, находится на `/cabinet/`.

## Шаги воспроизведения

1. Кликнуть «Выйти» в боковом меню ЛК.
2. Дождаться `POST /v2/logout` (реально уходит и отвечает `200
   {result:true, errors:[], data:null}` — успех согласно самому API).
3. Убедиться, что произошёл редирект на `/` (происходит стабильно).
4. Сделать `F5` (полный reload) на `/`.
5. Перейти напрямую на `/cabinet/`.

## Ожидаемый результат

После успешного логаута сессия должна быть реально завершена на бэкенде —
после reload и повторного захода на `/cabinet/` должна показываться
анонимная версия («Авторизуйтесь» / кнопка «Войти»), не данные аккаунта.

## Фактический результат

Воспроизведено многократно через автоматизированные повторные прогоны
(Cypress, реальный стенд, без моков):
- Первый прогон (4 попытки, без reload, только проверка сразу после
  редиректа): в 3 из 4 попыток шапка сайта сразу после редиректа
  показывала имя «Джон» вместо «Войти».
- Второй прогон (3 попытки, с явным reload): в 2 из 3 попыток после
  reload профиль оставался «Джон»; в третьей — исчез только после
  reload (т.е. до reload UI ошибочно показывал «уже вышел», хотя сессия
  на самом деле ещё была жива).
- Третий прогон (5 попыток, с ожиданием ответа `/v2/logout` перед
  проверкой + reload): **5 из 5** — `POST /v2/logout` каждый раз отвечал
  `200 {result:true}`, но после reload в шапке снова «Джон».
- Финальный прогон (4 попытки, логаут → reload → прямой заход на
  `/cabinet/`): **3 из 4** — прямой заход на `/cabinet/` после «логаута»
  показывает ПОЛНОЦЕННУЮ страницу личного кабинета с реальными данными
  аккаунта (баланс, «Личный кабинет» в меню и т.д.), а не анонимную
  версию — см. скриншот, это доказывает, что сессия реально жива на
  бэкенде, а не просто визуальный кэш на фронте.

Итого баг воспроизводится в большинстве попыток (примерно 11 из 16 по
всем прогонам), но не строго в 100% случаев — похоже на гонку в
инвалидации сессии на бэкенде (`POST /v2/logout` отвечает успехом до
того, как сессия/токен реально помечены недействительными, либо
инвалидация иногда не происходит вовсе).

## Скриншоты

`screenshots/bug034-cabinet-accessible-after-logout.png` — прямой заход
на `/cabinet/` после клика «Выйти» + reload: виден полноценный кабинет
(баланс 0/0, пункт «Личный кабинет» активен, «Мои заказы» и т.д.) вместо
ожидаемой анонимной версии.

## Вероятная причина

`POST /v2/logout` отвечает `200 {result:true}` немедленно, не дожидаясь
(или не гарантируя) реальной инвалидации сессии/токена на бэкенде —
классическая гонка между «ответить об успехе» и «фактически применить
эффект». С точки зрения ISTQB это дефект API: эндпоинт сигнализирует об
успехе, не выполняя корректно свою обязательную функцию.

## Автотест, фиксирующий баг

Не включён в основной набор `cabinet_overview.cy.js` — интермиттентность
(не 100%-я репродукция) делает жёсткий assert в общем прогоне
нестабильным без ретраев на уровне самого сценария (логаут → reload →
проверка, несколько попыток). Существующий тест «Выход из аккаунта по
пункту «Выйти»» проверяет только сразу-после-редиректа UI, без reload —
им баг ловится лишь частично (флейково). Требуется отдельный тест с
несколькими попытками (loop + retry), см. пример в разведке этого бага.
