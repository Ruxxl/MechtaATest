# BUG-024: PUT /v3/profile отвечает 204 (успех) на цифры/HTML/спецсимволы в Имени и Фамилии, но тихо НЕ сохраняет значение

**Раздел:** Личный кабинет — Редактирование профиля (модалка «Редактировать данные», `/cabinet/`)
**Severity:** High
**Приоритет:** High
**Статус:** Подтверждён
**Дата обнаружения:** 2026-08-07
**Окружение:** `http://d2.im.mdev.kz/cabinet/` → API `http://api.d.im.mdev.kz/v3/profile` (тестовый стенд d2)

## Предусловия

Пользователь авторизован, открыта модалка «Редактировать данные» (или прямой доступ к API `PUT /v3/profile`).

## Шаги воспроизведения

1. В поле «Имя» ввести значение, содержащее цифры, HTML-теги или спецсимволы,
   например `Иван123`, `<script>alert(1)</script>`, `Иван<b>`, `Иван&amp;`.
2. Нажать «Сохранить» (либо отправить эквивалентный `PUT
   http://api.d.im.mdev.kz/v3/profile` напрямую с телом
   `{"firstname":"Иван123", "lastname":"Appleseed", "birthdate":"2026-06-18",
   "gender":"1", "email":"ivanov@gmail.com"}`).
3. Проверить код ответа сервера и реальное значение поля повторным `GET
   /v3/profile`.

Воспроизведено одинаково для **обоих** полей — `firstname` и `lastname` — и
для нескольких вариантов «мусорного» содержимого (цифры, `<b>`, `&amp;`,
XSS-пейлоад `<script>alert(1)</script>`).

## Ожидаемый результат

Тот же контракт, что API уже корректно реализует для других невалидных
случаев на этом же эндпоинте (сверено в рамках этой же сессии):
- пустое/только-пробелы `firstname`/`lastname` → `422` с телом
  `{"error":{"code":"validation_error","message":"Поле firstname является
  обязательным."}}`;
- будущая `birthdate` → `422` (`validation.before_or_equal`);
- некорректный формат `email` → `422` с понятным сообщением;
- `gender` вне `{1,2}` → `422` (`validation.in`).

То есть либо значение с цифрами/HTML должно быть отклонено так же явно
(`422` + сообщение), либо, если бизнес-правило не запрещает цифры/спецсимволы
в имени, оно должно реально сохраняться при ответе `200/204`.

## Фактический результат

Сервер отвечает `204 No Content` (тот же код, что и при настоящем успешном
сохранении), но значение поля **не изменяется** — подтверждено немедленным
повторным `GET /v3/profile`. Никакой ошибки, предупреждения или иного
признака отказа в ответе нет — с точки зрения контракта API запрос выглядит
полностью успешным.

Фронтенд слепо доверяет статусу `204`: в UI показывается **тот же тост
«Успешно»**, что и при реальном сохранении, хотя фактически ничего не
изменилось. Пользователь получает ложное подтверждение того, что его данные
сохранены.

Пример воспроизведённой серии запросов (прямые вызовы API, тестовый
аккаунт «Джон Appleseed»):

| Отправлено `firstname` | Код ответа | Реальное значение после |
|---|---|---|
| `ИванТест` (чистые буквы) | 204 | `ИванТест` ✅ сохранилось |
| `Иван123` | 204 | осталось `ИванТест` ❌ не сохранилось |
| `Иван<b>` | 204 | осталось `ИванТест` ❌ не сохранилось |
| `Иван&amp;` | 204 | осталось `ИванТест` ❌ не сохранилось |
| `` (пусто) | **422** | (валидация сработала как надо) |
| `   ` (пробелы) | **422** | (валидация сработала как надо) |

## Вероятная причина

На бэкенде, судя по всему, есть отдельный слой санитизации/фильтрации имени
(вероятно, regex вида «только буквы»), который срабатывает ПОСЛЕ основной
валидации (`required`) и молча отбрасывает запись без единой ошибки, вместо
того чтобы либо вернуть `422` по аналогии с остальными правилами, либо
пропустить значение как есть.

## Почему это опасно

- Автотесты, которые проверяют только код ответа (`200`/`204` = «сохранилось»),
  систематически пропустят потерю данных.
- Реальный пользователь видит «Успешно» и уходит со страницы в уверенности,
  что его данные обновлены — узнает об обратном только при следующем визите
  в профиль.
- Поведение расходится с тем же самым эндпоинтом для других невалидных
  случаев, что говорит о непоследовательной обработке ошибок, а не о
  сознательном архитектурном решении.
