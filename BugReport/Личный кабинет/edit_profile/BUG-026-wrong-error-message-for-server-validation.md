# BUG-026: При реальной серверной 422-ошибке сохранения UI показывает не относящийся к делу тост «Ошибка получения данных» вместо текста ошибки поля

**Раздел:** Личный кабинет — Редактирование профиля (модалка «Редактировать данные», `/cabinet/`)
**Severity:** Medium
**Приоритет:** Medium
**Статус:** Подтверждён (Jira AS-4531, в работе — «Код ревью» на 2026-08-10)
**Дата обнаружения:** 2026-08-07
**Окружение:** `http://d2.im.mdev.kz/cabinet/` → API `http://api.d.im.mdev.kz/v3/profile` (тестовый стенд d2)

## Предусловия

Пользователь авторизован, открыта модалка «Редактировать данные». Значение,
которое клиент НЕ отфильтровывает собственной (чисто фронтовой)
валидацией, но которое сервер отклоняет — например, поле «Имя», состоящее
только из пробелов.

## Шаги воспроизведения

1. Полностью очистить поле «Имя» и ввести только пробелы (`"   "`).
2. Нажать «Сохранить».

(Для сравнения: если полностью ОЧИСТИТЬ поле, ничего не вводя, срабатывает
мгновенная клиентская проверка с текстом «Заполните поле — оно
обязательное» — БЕЗ похода в сеть. Этот баг про другой путь — когда
запрос реально уходит на сервер и сервер его отклоняет.)

## Ожидаемый результат

Поскольку поле фактически пустое (пробелы), ожидается либо клиентская
блокировка с тем же понятным сообщением «Заполните поле», либо (раз запрос
всё-таки ушёл на сервер) отображение серверного сообщения об ошибке под
полем — сервер уже возвращает корректный, понятный текст: «Поле firstname
является обязательным.» (см. также TC-API-029).

## Фактический результат

Запрос `PUT http://api.d.im.mdev.kz/v3/profile` реально уходит на сервер с
телом `{"firstname":"   ", ...}` и корректно получает `422` с телом
`{"error":{"code":"validation_error","message":"Поле firstname является
обязательным."}}` — то есть сервер отработал правильно. Но фронтенд
**не показывает это сообщение** пользователю. Вместо этого в углу экрана
появляется красный тост с текстом **«Ошибка получения данных»** — сообщение,
не относящееся ни к этому полю, ни вообще к операции сохранения (текст
скорее подходит для ошибки GET-запроса). Значение, разумеется, не
сохраняется (это не баг само по себе), но пользователь не понимает,
что именно пошло не так и как это исправить.

## Вероятная причина

У фронтенда, судя по всему, нет обработчика для маппинга структуры
`{error:{code,message}}` от сервера на конкретное поле формы — есть только
жёстко закодированные клиентские проверки (пустая строка, формат email) и
один общий fallback-тост на любую прочую ошибку сети/API, с неточным
текстом.

## Автотест, фиксирующий баг

`cypress/e2e/main_test/cabinet/edit_profile.cy.js`, describe-блок
«Редактирование профиля — клиентская валидация» — тест на пробелы в имени
ожидает содержательное сообщение об ошибке и фиксирует фактическое
поведение (баг), пока не исправлено.
