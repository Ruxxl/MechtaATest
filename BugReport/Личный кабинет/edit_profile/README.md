## Автотест

`cypress/e2e/Regress_Test/cabinet/edit_profile.cy.js`, page object
`cypress/support/pageObjects/editProfilePage.js`, API-хелперы
`getProfile`/`putProfile`/`profileFieldsMap` в `cabinetApi.js`.

25 тестов, стабильно **21 passing / 4 failing** (подтверждено 2 чистых
прогона подряд) — все 4 падения намеренные и точно соответствуют трём
багам: 2 теста на BUG-024 (сервер должен отвечать 422, а не 204, на
цифры/HTML в имени/фамилии), 1 на BUG-025 (карточка не обновляется без
reload), 1 на BUG-026 (неверный текст ошибки). У BUG-024 есть ещё третий,
ПРОХОДЯЩИЙ тест — он в виде исключения фиксирует фактическое (баговое)
поведение напрямую (тост «Успешно» реально показывается), а не «падает,
пока не почини»: тост на этой странице сам скрывается через несколько
секунд (auto-dismiss), из-за чего надёжно проверить его ОТСУТСТВИЕ через
`.should('not.exist')` невозможно — эта проверка на разных прогонах давала
то ложный pass (проверили раньше, чем тост успел появиться), то ложный pass
по другой причине (проверили уже после того как он сам исчез). Позитивная
проверка `.should('be.visible')` со встроенным retry — единственный
надёжный способ поймать этот конкретный тост.

## Разведка сети (открытие/сохранение/обновление)

Полная разведка реального контракта — в памяти проекта
(`project_lk_testing_d2_stand`), кратко:
- Открытие модалки: `GET /v3/profile` → `{fields:[{name,label,placeholder,
  type,value,validation[],data{}}]}`.
- Сохранение: `PUT /v3/profile` (не POST/PATCH), тело
  `{firstname,lastname,birthdate,gender,email}` — `gender` строкой,
  `contact_phone` не отправляется. Успех — `204` без тела.
- Обновление: фронт сам делает повторный `GET /v3/profile` сразу после
  успешного `PUT` — это подтверждено, но, как показывает BUG-025, эта
  повторная выборка обновляет только СОСТОЯНИЕ МОДАЛКИ, не родительские
  компоненты страницы.
- Реальная серверная валидация 422 подтверждена корректной для:
  пустое/пробелы-only firstname/lastname, будущая дата рождения, битый
  email, gender вне `{1,2}` — во всех случаях кроме «цифры/HTML в имени»
  (BUG-024) и кроме отображения на UI (BUG-026 — сервер прав, фронт неверно
  показывает ошибку).

## Что НЕ было протестировано (и почему)

- **Прямой ввод даты рождения через календарь** (TC-029..041) — поле
  «Дата рождения» на самом деле не текстовый инпут, а кнопка-триггер
  календаря (Reka UI popover); сложные сценарии переключения месяцев/лет
  не автоматизированы, только базовое отображение и серверная валидация
  границы (будущая дата) — через прямой API, как и рекомендует сам xlsx
  (Примечание №11).
- **Email-уникальность** (TC-060/TC-API-027) — xlsx предполагает, что
  `test@mail.com` уже занят другим аккаунтом; на этом стенде это не
  подтвердилось (email сохранился без ошибки) — нужен реальный второй
  зарегистрированный аккаунт, чтобы проверить это по-настоящему.
- **27 кейсов «Комбинации полей»** (TC-CMB-001..027) — покрыта только
  показательная часть (TC-CMB-001-класс — комбинированное сохранение
  нескольких валидных полей за один запрос); полная матрица
  валидно/невалидно по всем 5 полям не автоматизирована — типовой паттерн
  (частичная валидация блокирует всю форму) уже виден в TC-006/TC-007/
  BUG-026 тестах и распространяется на комбинации логически так же.
