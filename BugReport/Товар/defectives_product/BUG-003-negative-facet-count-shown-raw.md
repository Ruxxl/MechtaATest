# BUG-003: Отрицательный счётчик у фасета фильтра отображается как есть, без санитизации

**Severity:** Low
**Статус:** Подтверждён (только через мок, реальных отрицательных счётчиков в данных не наблюдалось)
**Окружение:** pp.yc.mechta.kz (preprod)
**Дата:** 2026-08-06

## Затрагивает кейс теста-плана

FLT-032 (Лист 8 "Фильтры каталога").

## Описание

Если API `/catalog/filter` отдаёт отрицательное значение `count` для опции
фильтра (гипотетическая аномалия данных MDM/бэкенда), фронтенд отображает
это число как есть, без какой-либо защиты: чекбокс "Honor" рендерится с
текстом `"Honor-3"` (норма — `"Honor3"`, где "3" — реальный счётчик).

## Шаги воспроизведения

1. Замокать `GET /api/v3/catalog/filter?slug=defective-smartfony-i-gadjety`
   так, чтобы `properties[brend].items[].count` для Honor стал `-3`.
2. Открыть `/section/defective-smartfony-i-gadjety/`.
3. Посмотреть на чекбокс "Honor" в блоке "Бренд".

## Ожидаемый результат

Отрицательное число не должно отображаться рядом с чекбоксом — значение
следует трактовать как 0, либо чекбокс должен скрываться/дизейбл.

## Фактический результат

Чекбокс показывает `"Honor-3"` — сырое отрицательное число без обработки.

## Примечание

Реальных отрицательных счётчиков в данных не встречалось за время тестирования
— находка подтверждена только через мок API. Это гипотетический edge case
(аномалия данных на стороне MDM/бэкенда), а не наблюдаемый в проде дефект;
severity понижена до Low. Ценность — фронтенд не имеет defensive-проверки на
этот случай, стоит добавить `Math.max(0, count)` или аналог при рендере.

## Зафиксировано автотестом

— тест `FLT-032 / БАГ` целенаправленно ожидает отсутствие отрицательного
числа и падает, пока не добавлена защита.
