# BUG-004: Страница акции (детальная) зависает в бесконечной загрузке при переходе по ссылке с фильтрами, дающими 0 результатов

**Раздел:** Акции — Детальная страница акции (`/useful/shares/{slug}/`)
**Severity:** Medium
**Приоритет:** Medium
**Статус:** Подтверждён (воспроизведён напрямую через API и через прямой переход по URL в браузере)
**Дата обнаружения:** 2026-08-04

## Окружение

- URL (пример 1, невалидное значение фильтра):
  `https://pp.yc.mechta.kz/useful/shares/bonusy-za-otzyv/?category=uborka-doma&properties[brend][]=this-brand-does-not-exist-xyz`
- URL (пример 2, полностью ВАЛИДНЫЕ фильтры, которые просто не пересекаются):
  `https://pp.yc.mechta.kz/useful/shares/bonusy-za-otzyv/?category=uborka-doma&properties[brend][]=gorenje&properties[discount][]=has_discount`
- Реальный backend-запрос, который вызывает фронтенд:
  `GET https://www.mechta.kz/api/v3/catalog/products?slug=uborka-doma&...&properties[brend][]=gorenje&properties[discount][]=has_discount`
- Как это достижимо пользователем: переход по сохранённой/скопированной/присланной ссылке с параметрами фильтра в query string (например, ссылка из чата поддержки, закладка, sharing-ссылка от другого пользователя, ссылка из письма рассылки). Через обычный клик по чекбоксам в UI эта комбинация недостижима (см. "Связанное наблюдение" ниже) — но прямой переход по URL полностью реален.

## Предусловия

Пользователь открывает `/useful/shares/{slug}/` с query-параметрами `category` + `properties[...][]`, для которых пересечение результатов равно 0 — либо потому что указано несуществующее значение фильтра, либо потому что выбрана валидная, но взаимоисключающая комбинация двух реальных фильтров.

## Шаги воспроизведения

1. Открыть `https://pp.yc.mechta.kz/useful/shares/bonusy-za-otzyv/?category=uborka-doma&properties[brend][]=gorenje&properties[discount][]=has_discount`
   (бренд Gorenje в этой подкатегории — count=1, но ни один товар Gorenje не имеет скидки — пересечение 0, подтверждено напрямую через API `/api/v3/catalog/filter`, где `discount.items` для Gorenje возвращает `count:0`)
2. Подождать 5-10 секунд.

## Ожидаемый результат

Один из вариантов корректной обработки:
- Страница показывает дружелюбное сообщение «Товары не найдены» / «По вашему запросу ничего не найдено», **или**
- Список фильтров отображается, но область товаров явно показывает пустое состояние с возможностью сбросить фильтры.

В любом случае страница должна закончить загрузку и не оставаться в подвешенном состоянии.

## Фактический результат

1. **Backend корректно отвечает `204 No Content` с пустым телом** на запрос `/api/v3/catalog/products` — это валидный и ожидаемый ответ backend'а для случая "результатов нет" (подтверждено напрямую через `fetch` с теми же заголовками, что использует сайт).
2. **Фронтенд не обрабатывает пустой/204-ответ** — блоки товаров (карточки) навсегда остаются в skeleton-состоянии загрузки (серые плейсхолдеры), даже спустя 10+ секунд. Пользователь не получает никакой информации о том, что товаров по этому фильтру нет — просто бесконечный "лоадер".
3. Блок цены (`Цена`) при этом корректно обновляется до `0 / 0` — то есть часть страницы (фильтры) знает о нулевом результате, но область товаров не реагирует на это состояние вообще.

Проверено на двух независимых примерах (невалидное значение бренда и валидная взаимоисключающая пара бренд+скидка) — поведение идентично в обоих случаях.

## Скриншоты

- `screenshots/bug004-detail-filter-infinite-loading.jpg` — зависшие skeleton-плейсхолдеры карточек товаров спустя 4+ секунды после перехода по ссылке с валидными, но взаимоисключающими фильтрами (`brend=gorenje` + `discount=has_discount`), при этом блок «Цена» уже показывает `0/0`

## Вероятная причина

Backend отвечает `204 No Content` вместо `200 OK` с пустым массивом `products: []` для случая нулевого пересечения. Судя по поведению, код фронтенда, ожидающий JSON-тело в ответе (`products`, `meta` и т.д.), либо падает на попытке распарсить пустое тело, либо просто никогда не получает данные, необходимые для перехода из `loading` в `empty`-состояние — и стейт загрузки остаётся `true` навсегда. Это отдельный, самостоятельный дефект от BUG-001 (тот — про каталог акций и коды 422/500), но того же класса: отсутствие обработки нестандартных/пустых ответов API для блока карточек.

## Связанное наблюдение (важно для интерпретации — НЕ баг само по себе)

Через обычное взаимодействие с UI (клик по чекбоксам) эта ситуация недостижима: как только пользователь выбирает бренд Gorenje, чекбокс «Есть скидка → Да» получает счётчик `0` и переходит в состояние `disabled` (нативный HTML-атрибут `disabled` на `<button role="checkbox">`, `cursor-not-allowed`) — кликнуть по нему невозможно. Это ПРАВИЛЬНОЕ, ожидаемое поведение (аналогично `pointer-events:none` у категорий/видов акций в каталоге, см. CAT-015/016) и не является багом — наоборот, это единственный механизм, который вообще не даёт пользователю самостоятельно построить такую ссылку через интерфейс. Баг проявляется только при прямом переходе по URL, сформированному не через UI сайта.

## Автотест, фиксирующий баг

`cypress/e2e/main_test/actions/action_filters.cy.js` → `FP-054` (прямой переход по URL с невалидным значением фильтра) и `FP-031` (валидные, но взаимоисключающие 2+ фильтра, дающие пересечение 0) — оба теста целенаправленно проверяют ОЖИДАЕМОЕ поведение (страница должна показать пустое состояние, а не зависнуть) и в текущем состоянии фронтенда падают, документируя баг.
