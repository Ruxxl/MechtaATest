# BUG-005: `GET /api/v3/promotions/{slug}/categories` возвращает `500 Internal Server Error` вместо `4xx` для «не найдено»/невалидного slug

**Раздел:** Акции — API-контракт (`GET /api/v3/promotions/{slug}/categories`)
**Severity:** Low
**Приоритет:** Low
**Статус:** Подтверждён (переподтверждён напрямую через `curl` 2026-08-04 на трёх независимых сценариях)
**Дата обнаружения:** 2026-08-03 (изначально задокументирован как "не баг"), переклассифицирован в баг 2026-08-04

## Окружение

- `GET https://www.mechta.kz/api/v3/promotions/{slug}/categories`
- Заголовки: `Accept: application/json`, `X-City-Code: astana`
- Воспроизведено на трёх разных невалидных значениях `slug`:
  1. Несуществующий, но синтаксически нормальный slug: `this-promo-does-not-exist-xyz-123`
  2. Slug с кириллицей и пробелом: `акция тест`
  3. Очень длинный slug (2000+ символов): `aaaa...a`

## Предусловия

Клиент (не обязательно фронтенд mechta.kz — любой потребитель этого публичного API) запрашивает список категорий для акции по slug, которого не существует или который заведомо некорректен.

## Шаги воспроизведения

```bash
curl -s -o /dev/null -w "%{http_code}\n" \
  "https://www.mechta.kz/api/v3/promotions/this-promo-does-not-exist-xyz-123/categories" \
  -H "Accept: application/json" -H "X-City-Code: astana"
```

## Ожидаемый результат

Для ситуации «акция с таким slug не найдена» или «slug синтаксически некорректен» API должен отвечать кодом семейства `4xx` (`404 Not Found` для первого случая, `400 Bad Request` для некорректного формата) — то есть кодом, который явно относит проблему к клиентскому запросу.

## Фактический результат

Во всех трёх сценариях API отвечает `500 Internal Server Error`, при этом тело ответа осмысленное и корректно описывает причину:

```json
{"error":{"code":"promotion_not_found","message":"Акция с кодом this-promo-does-not-exist-xyz-123 не найдена"}}
```

То есть backend **знает**, что это ситуация «не найдено» (правильный `error.code` и понятное сообщение), но всё равно сигнализирует об этом кодом состояния `500`, который по HTTP-семантике означает «сбой на стороне сервера», а не «клиент запросил несуществующий ресурс». Это некорректная обработка ошибки на уровне самого API: код ответа не соответствует реальной причине.

## Почему это баг, а не просто особенность контракта

Раньше этот случай был сознательно НЕ оформлен как баг, так как реальная детальная страница акции с таким slug у пользователя корректно и незаметно редиректит на список акций — то есть фронтенд не ломается. Однако критерий бага не ограничивается фронтенд-обработкой: некорректный код ответа на уровне самого API — это самостоятельный дефект (`500` вместо `4xx` для ситуации, которая явно НЕ является сбоем сервера), независимо от того, как с ним справляется конкретный текущий фронтенд. Любой другой клиент этого API (мобильное приложение, партнёрская интеграция, будущая версия фронтенда) может отреагировать на `500` иначе — например ретраить запрос как временный сбой, что для по-настоящему несуществующего ресурса бессмысленно и создаёт лишнюю нагрузку.

## Скриншоты

Не применимо (чистый API-дефект, не воспроизводится в UI).

## Вероятная причина

Похоже, что обработчик эндпоинта ловит исключение «акция не найдена» (судя по чистому и специфичному `error.code`) слишком поздно — уже на уровне общего error-handler'а, который по умолчанию отдаёт `500` для любого необработанного исключения, вместо того чтобы явно маппить `promotion_not_found` на `404`.

## Автотест, фиксирующий баг

`cypress/e2e/Regress_Test/actions/api_categories.cy.js` → `API-CT-008`, `API-CT-010`, `API-CT-011` — все три целенаправленно ожидают код `4xx` и падают на фактическом `500`, документируя баг на уровне API-контракта.
