# BUG-001: Страница «Акции» зависает в состоянии загрузки при ЛЮБОЙ ошибке ответа /promotions (422 и 500)

**Раздел:** Акции — Каталог (страница списка акций)
**Severity:** High
**Приоритет:** High
**Статус:** Подтверждён (воспроизведён 3 раза подряд на чистых вкладках для 422; дополнительно подтверждено для форсированного 500)
**Дата обнаружения:** 2026-08-03
**Обновлено:** 2026-08-04 — подтверждено, что баг не специфичен для 422/невалидного `type`, а является общим отсутствием обработки ошибок ответа `/promotions` (см. "Дополнительное подтверждение" ниже)

## Окружение

- URL: `https://pp.yc.mechta.kz/useful/shares/?type=<любое_неизвестное_значение>`
- Пример: `https://pp.yc.mechta.kz/useful/shares/?type=garbage_type_123`
- Реальный backend API, который вызывает фронтенд: `GET https://www.mechta.kz/api/v3/promotions?type=garbage_type_123`
- Как это достижимо пользователем: битая/устаревшая ссылка на фильтр акций (закладка, реклама, письмо рассылки, внешняя ссылка с опечаткой в параметре) — параметр `type` не валидируется на фронте перед отправкой в URL.

## Предусловия

Пользователь (авторизованный или нет — не влияет) переходит по прямой ссылке на страницу акций с параметром `type`, значение которого не входит в список поддерживаемых бэкендом типов (`all, gift, preorder, cashback, discount, recommendations, new`).

## Шаги воспроизведения

1. Открыть `https://pp.yc.mechta.kz/useful/shares/?type=garbage_type_123`
2. Подождать загрузку страницы (проверено — зависание сохраняется после 5+ секунд ожидания)

## Ожидаемый результат

Один из вариантов корректной обработки:
- Параметр с невалидным значением игнорируется, показывается список акций без фильтра по типу (аналогично тому, как это происходит для несуществующего значения `category`, см. ниже "Связанное наблюдение"), **или**
- Показывается дружелюбное сообщение «Акции не найдены» / «Не удалось загрузить акции. Попробуйте позже», как это описано в требованиях для ошибок сети (см. лист тест-кейсов CAT-049).

В любом случае страница должна закончить загрузку и не оставаться в подвешенном состоянии.

## Фактический результат

1. **Backend возвращает `422 Unprocessable Entity`** с телом:
   ```json
   {"error":{"code":"validation_error","message":"The selected type is invalid."}}
   ```
   Подтверждено напрямую через API (см. `cypress/e2e/main_test/actions/api_promotions.cy.js`, тест `API-PR-021`).

2. **Фронтенд показывает пользователю сырой технический текст ошибки на английском языке** — `"validation_error" / "The selected type is invalid."` — во всплывающем тосте. Это внутренний код и сообщение backend'а, никогда не предназначавшиеся для показа конечному пользователю, да ещё и не переведённые на русский/казахский (весь остальной интерфейс — на русском).

3. **Блоки категорий, "Виды акций" в сайдбаре и список карточек акций навсегда остаются в skeleton-состоянии загрузки** (серые плейсхолдеры) — контент никогда не отрисовывается. Кнопка "Показать ещё" остаётся задизейбленной. Страница фактически неюзабельна по этой ссылке.

Воспроизведено идентично 3 раза подряд на свежих вкладках (без общего состояния/кэша между попытками).

## Вероятная причина

Судя по прямым запросам к API, для большинства "пустых" сценариев (например, несуществующий `category`) backend отвечает `200 OK` с `"promotions": null`, и фронтенд, похоже, справляется с этим (хотя и не показывает сообщение "Акции не найдены" — см. связанное наблюдение ниже). Но для невалидного `type` backend отвечает `422`, и код обработки ошибок на фронте, судя по всему, либо не покрывает статус 422 для этого запроса, либо показывает необработанное сообщение из ответа сервера напрямую, при этом не сбрасывая состояние загрузки (`loading = true` так и остаётся).

## Дополнительное подтверждение: то же самое при реальном 500 от backend'а (не только 422)

Форсированный через `cy.intercept` ответ `500` на `GET /promotions` (эмуляция реального сбоя backend'а,
без завязки на конкретное значение query-параметров) приводит к ТОЧНО ТАКОМУ ЖЕ зависанию: баннер
рисуется, но блок категорий, сайдбар "Виды акций" и список акций навсегда остаются в skeleton-состоянии,
кнопка "Показать ещё" видна, но неактивна, никакого сообщения об ошибке пользователь не видит.
Это доказывает, что дефект — не частный случай обработки конкретного 422/`type`, а общее отсутствие
error-состояния для блока акций: при ЛЮБОЙ ошибке ответа `/promotions` (что 422, что 500) фронтенд
просто никогда не выходит из состояния загрузки. Тест: `cypress/e2e/main_test/actions/integration.cy.js`
→ `INT-010`.

## Связанное наблюдение (не оформлено отдельным багом — тот же класс проблемы, но не самостоятельный дефект)

Для `?category=<несуществующая_категория>` backend отвечает `200 OK` с `"promotions": null`. Фронтенд в этом случае не зависает в skeleton, но и не показывает сообщение «Акции не найдены» — область карточек акций остаётся пустой без какой-либо обратной связи для пользователя. Автотест `CAT-017` в `cypress/e2e/main_test/actions/catalog.cy.js` фиксирует это как несоответствие ожиданиям (тест-кейс требует явное сообщение «Акции не найдены»).

## Автотест, фиксирующий баг

`cypress/e2e/main_test/actions/catalog.cy.js` → тест `CAT-019 / негативный: невалидный type в URL не должен ломать страницу` — тест целенаправленно проверяет ОЖИДАЕМОЕ поведение (контент должен отрисоваться, без сырых технических сообщений) и в текущем состоянии бэкенда/фронтенда падает, документируя баг. Тест должен начать проходить автоматически после исправления.
